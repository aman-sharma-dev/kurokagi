# Configuration schema version 3

The complete working example is [`examples/config.yaml`](../examples/config.yaml). Schema v2 configs are rejected; result JSON remains schema v2. Unknown YAML/JSON fields are rejected. Credentials may use identity headers or credential providers and should be supplied through `${ENV_VAR}` references.

## Horizontal resource checks

Each `resources` item explicitly sets:

- `name`: unique mapping identifier.
- `classification`: `BOLA`, `IDOR`, or `RELATIONSHIP`, carried unchanged to finding metadata.
- `collection` and `detail`: in-scope OpenAPI paths; detail placeholders must match configured identifier parameters.
- Either legacy `id_field` / `verify_field` or `identifier_fields` / `verification_fields`. Composite identifier entries contain `path` and `parameter`; all configured fields are explicit JSON paths, with dot notation for nested objects.
- `ownership`: currently only `collection_visibility`.
- Optional `relationships`: entries contain a unique `name`, explicit `kind` (`tenant`, `organization`, `workspace`, `project`, `parent`, or `child`), and JSON `field`. Values are compared to identity `contexts` using that relationship name. Context values never enter result JSON.
- Optional `ignore_fields`: explicit JSON paths omitted from structured differential evidence (for example volatile timestamps). Differential output contains field paths, never compared values, and cannot independently create a finding.
- Optional `pagination`: explicit `type` (`page`, `offset`, or `cursor`), corresponding parameter names, `page_size`, and `max_pages`. Cursor mode also needs `next_cursor_field`. Bounds are constrained by global request and object limits; cap exhaustion is inconclusive.

`expectations` entries require `identity`, `resource`, and `access` (`ALLOWED`, `DENIED`, or `UNKNOWN`). `method` selects the HTTP operation; when omitted it means `GET` to preserve existing GET configurations. Optional `owner` scopes the rule to one victim identity; optional `relationship` selects one configured relationship boundary. Actor/owner/resource/relationship/method rules are distinct. A relationship finding requires complete resource and actor context, a different boundary, positive composite-ID and verification evidence, and an explicit `DENIED` GET expectation. Only explicit `DENIED` can produce a finding.

## Vertical read-only checks

Optional authorization `operations` entries require `id`, literal in-scope `path`, `method`, `actor`, `classification`, `access`, and `verification`. Methods are normalized to uppercase and limited to GET, POST, PUT, PATCH, and DELETE. Method safety is derived: GET is `READ_ONLY`, POST/PUT/PATCH are `MUTATING`, and DELETE is `DESTRUCTIVE`; safety labels are not configurable. `verification.type` accepts `RESPONSE_FIELD`, `RESOURCE_EXISTS`, `RESOURCE_STATE`, or `RESOURCE_ABSENT`; `field` is required for `RESPONSE_FIELD` and `RESOURCE_STATE`. GET plus `RESPONSE_FIELD` runs as before. POST runs only through the controlled lifecycle below. PUT/PATCH and explicitly enabled controlled DELETE run only through a linked scanner-created resource lifecycle; arbitrary DELETE operations remain unsupported. Replace the former `success_field` with `verification: {type: RESPONSE_FIELD, field: ...}`. The scanner does not infer policy from method, path, role, tags, or identity name.

Controlled POST remains disabled unless the `mutations` policy is enabled with POST in its explicit method allowlist, explicit mutation and cleanup path allowlists, and bounded request budgets. The `RESOURCE_EXISTS` strategy must configure `path`, `marker_field`, `request_marker_field`, `resource_id_field`, `baseline_complete_field`, and `cleanup_path`. The explicit JSON request body must put `${KURO_TEST_MARKER}` at `request_marker_field`; Kuro renders a random test marker there. `baseline_complete_field` must name a field whose value is boolean `true` in both the successful in-scope baseline and post-operation verification responses. The baseline must not contain the marker. Kuro then sends exactly one POST and verifies state through the configured safe GET. A finding requires explicit `DENIED` and exactly one observed resource containing the marker. POST redirects are not followed; POST is never retried. When proof establishes a scanner-created resource, Kuro can send one cleanup-only DELETE to the separately allowlisted cleanup path. DELETE redirects are not followed and DELETE is never retried. A complete safe GET must confirm the marker and resource ID are absent; status alone is insufficient. Cleanup outcomes are exposed in coverage, and cleanup failure or uncertainty makes completion partial while preserving any finding.

**Enabled mutations can leave state if cleanup fails or cannot be verified.** Use enabled mutation configurations only with local controlled fixtures for end-to-end testing. PUT/PATCH and DELETE run only through the linked controlled-resource lifecycle below.

### Controlled PUT/PATCH

To opt in to a controlled update, keep the POST setup operation and add one PUT or PATCH operation that references it with `controlled_resource_operation_id`. The setup must be an explicitly configured `ALLOWED` POST for the same resource. The update path and state-verification path each use exactly one `{id}` parameter; the ID is filled only from the proven handle. Add the update method and exact path to `mutations.allowed_methods` and `mutations.allowed_paths`. Configure `verification.type: RESOURCE_STATE`, its safe GET `path`, scalar `field`, `baseline_complete_field`, and the same `resource_id_field` and `marker_field` used by the setup. Each pre/post state proof must contain that exact fresh marker and ID together on one unambiguous object. The explicit JSON request body must set that field to the intended test value. If it already equals the value in the complete pre-state GET, Kuro skips the write. The request budget must cover setup and one attack mutation; budget preflight checks that global and lifecycle budgets can cover the full sequence before creating the test resource.

When restoration is desired, configure `restore_body` as explicit JSON with `${KURO_PREVIOUS_STATE}` at the configured state field; `cleanup_request_budget` must be at least four for restoration plus cleanup and their verification requests. Kuro plans both restoration and fallback cleanup before issuing the PUT/PATCH, restores using a separate single-use capability, and verifies the original field with a safe GET. If no restoration body is configured, the scanner uses the setup operation's explicitly allowlisted proof-bound cleanup path. All mutation and lifecycle requests count against their bounded budgets. PUT/PATCH redirects are not followed and requests are never retried. Findings require an explicit `DENIED` expectation and a safe-GET verified transition; cleanup/restoration errors do not erase findings and make completion partial.

### Controlled DELETE authorization

Set `disposable: true` on the POST setup to declare the created test resource disposable. This declaration alone does not authorize deletion; the live marker proof and handle remain mandatory. Add `DELETE` to `mutations.allowed_methods` and list its exact `{id}` path in `allowed_paths`. Configure a DELETE operation with `controlled_resource_operation_id` pointing to the explicitly `ALLOWED` POST setup, plus explicit `access` and `classification`. The DELETE verification uses `type: RESOURCE_ABSENT`, a scoped detail GET `path` with exactly one `{id}`, and the setup's same `marker_field`, `resource_id_field`, and `baseline_complete_field`. The actor may differ from the setup actor, allowing explicit BOLA/IDOR/BFLA or relationship checks.

Before dispatch, the setup identity performs a fresh complete GET that proves the exact generated marker and resource ID. Kuro issues one DELETE for the configured attack actor, then uses bounded safe GET verification. Status alone never proves deletion. Only `DENIED` plus positively verified absence creates a finding. If the resource remains, Kuro uses the separate proof-bound cleanup DELETE; if absence is verified, it never sends cleanup DELETE. Unknown state is reported as inconclusive and is not blindly deleted. The global request, mutation, and cleanup budgets must cover the entire controlled lifecycle. DELETE redirects are not followed and retries are disabled.

Identity credentials may use static `headers` or `credentials` entries of type `header`, `bearer`, or `cookie`. Values support `${ENV_VAR}` expansion. `contexts` contains explicit relationship boundary values; configure only values required for the scan.

## Safety limits

Targeted retesting uses the current operation/configuration and fresh resource proofs. Historical IDs, credentials, request bodies, capabilities, and scope are not replayed. Outcomes, cleanup behavior, supported mutation lifecycles, and versioned retest output are described in [retesting](retesting.md) and [the retest result schema](retest-result-schema.json).

Origins and path prefixes are explicit and fail closed. `limits` bounds request count, concurrency, rate, timeout, response bytes, object count, and redirect behavior. GET and policy-authorized controlled POST/PUT/PATCH/DELETE lifecycles are available; arbitrary mutation execution is blocked. OpenAPI local JSON-Pointer refs are resolved; external refs are rejected without fetching. OpenAPI server URLs and security schemes are metadata only and never choose a request destination. See [the result schema](result-schema.json) for the machine output contract.
