# Architecture and safety model

Kurokagi implements bounded API authorization testing through this pipeline:

1. Strict JSON/YAML configuration and bounded OpenAPI 3.0/3.1 loading with local JSON-Pointer reference resolution and scanner-relevant operation metadata.
2. Explicit collection/detail operation selection and identity configuration.
3. Origin, path, request-count, rate, concurrency, timeout, response-size, and redirect enforcement in the HTTP executor.
4. Explicit composite identifier and verification tuple extraction, collection visibility comparison, and bounded page/offset/cursor discovery.
5. Actor/victim expectation lookup and conservative evidence evaluation for BOLA/IDOR; explicit context comparisons for relationship findings.
6. Method-aware configured authorization operations. GET with `RESPONSE_FIELD` runs. POST runs only through the controlled marker/baseline/verification lifecycle. PUT/PATCH run only when linked to a proven POST-created resource and are guarded by single-use state-bound capabilities. DELETE attack runs only against a disposable resource proven through that current POST lifecycle; arbitrary DELETE remains unsupported.
7. Targeted retesting resolves historical findings only to semantic selectors. Current configuration and fresh discovery/control proofs decide execution. Mutation retesting uses a new marker and resource lifecycle; no historical body, identity credential, runtime ID, scope, or capability is authority.
8. Separate finding, evidence, coverage, and versioned structured result output.

Authorization policy is never inferred from names, paths, tags, roles, status similarity, or OpenAPI security metadata. Only an explicit `DENIED` expectation plus proof that a uniquely established victim resource was returned can create a horizontal finding. Ambiguous or incomplete proof is inconclusive. Credentials and response bodies are excluded from output; evidence uses hashes and a content-type allowlist.

The operation/request model represents GET, POST, PUT, PATCH, and DELETE, with safety derived from method. The transport independently rejects mutating requests without internal capabilities. POST requires a single-use capability bound to the explicitly configured setup operation, rendered body, scan, and complete marker-absent baseline. POST redirects are not followed and POST is never retried. Safe GET verification must observe exactly one resource with the generated marker and a safe ID. Controlled PUT/PATCH operations must link to that POST setup, capture one configured scalar field from a complete and unambiguous resource GET, skip no-op transitions, and use method/resource/path/body/pre-state-bound single-use capabilities. Controlled DELETE has a separate attack capability bound to scan, operation, actor, expectation, classification, path, and the exact handle; fresh complete marker+ID proof immediately precedes its sole dispatch. A safe GET determines present/absent/unknown state. Only explicit DENIED plus verified disappearance is a finding. Verified disappearance bypasses cleanup, while a verified remaining resource may receive one separately authorized cleanup DELETE. Cleanup and restoration are bounded, budgeted, never retried, and do not follow redirects. Arbitrary-resource DELETE remains blocked. Failures are surfaced as partial completion without erasing a finding. End-to-end mutation fixtures must be local and controlled. Relationship authorization and pagination are implemented. Differential evidence is supporting only. External refs are rejected and never fetched. OpenAPI servers/security metadata never alter the request scope. See the README for the supported surface and limitations.
